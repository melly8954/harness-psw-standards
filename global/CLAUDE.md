# Global Harness

모든 프로젝트에서 문서 설계·수정·검증 작업을 일관되게 수행하기 위한 전역 진입 규칙이다.

이 문서에는 상세 설계 절차를 중복해서 작성하지 않는다.
세부 규칙은 공통 실행 규칙과 각 전역 스킬에서 관리한다.

## 규칙 우선순위

다음 순서로 적용한다.

1. 사용자의 현재 요청
2. 프로젝트 루트 `CLAUDE.md`
3. 프로젝트의 기준 문서
4. 전역 하네스 규칙
5. 개별 스킬의 기본 규칙

프로젝트별 규칙은 이 전역 규칙보다 우선한다.

제품 정책, 기술 구조, 데이터 모델, API와 UI의 실제 결정은 해당 프로젝트의 `docs/`를 기준으로 한다.

## 하네스 사용

**하네스 스킬은 전역에 설치하지 않는다.** 전역 설치는 모든 프로젝트에 걸려
프로젝트별 방법론과 섞인다. 필요한 프로젝트의 `.claude/skills/`에만 둔다.

정본 저장소는 `C:\psw\github\agent-harness-standards`다.

### 현행 하네스 (`skills/`)

문서 기반 하네스를 구축·재구축한다. 조사·계획·초안·검토는 대상 파일을 수정하지 않고,
사용자 승인 후에만 반영한다.

```text
harness-init      신규 구축 오케스트레이터 — 아래 5종을 고정 순서로 진행
harness-scan      프로젝트 사실·근거 수집
harness-plan      문서 트리와 파일별 처리 계획 결정
harness-draft     선택된 문서의 근거 기반 초안
harness-review    초안 검증과 인터뷰 질문 일괄 정리
harness-compose   승인된 문서와 루트 지시서 반영
harness-rebuild   기존 하네스 감사·마이그레이션·재구축
```

문서 골격은 `harness-init/references/templates/`가 소유한다
(prd · architecture · api · erd · conventions · testing · operations · security · decisions).

### v0 하네스 (`legacy/`)

문서 1종당 스킬 1개 구조의 1세대다. **신규 구축에 쓰지 않는다.**
현행 하네스가 덮지 않는 것이 남아 있어 보존한다 — 화면·UI 설계(`app-design`)와
각 도메인의 심층 규칙(API 항목 기준·상태 변경 API·엔터티 항목 기준 등).

v0 산출물을 이미 가진 프로젝트에서만 쓴다. 대상과 설치법은
`agent-harness-standards/legacy/README.md`가 소유한다.

v0 스킬은 아래 공통 규칙을 하드 참조하므로 이 파일들은 전역에 유지한다.
자동 로드되지 않고 스킬이 요청할 때만 읽힌다.

```text
~/.claude/harness/common-execution-rules.md
~/.claude/harness/harness-structure.md
```

`harness-structure.md`는 하네스 초기화, 전체 감사, 문서 체계 변경 또는
구조 확인이 필요한 경우에만 읽는다.

### 납품 파이프라인 (별도 체계)

메타소프트 납품 사업은 하네스가 아니라 `C:\psw\metasoft\metacodex`의
딜리버리 파이프라인을 따른다. 스킬 10종이 전역에 설치되어 있고
(`rfp-analyze`·`func-spec`·`feature-def`·`prototype-run`·`implement-fn`·
`verify-delivery`·`sla-ops`·`wbs-gen`·`pm-report`·`local-standards`),
진입 문서는 그 저장소의 `CLAUDE.md`다. **하네스와 섞어 쓰지 않는다** —
산출물 위치와 문서 체계가 다르다.

요청과 관계없는 스킬이나 전역 문서를 예방적으로 읽지 않는다.

## 컨텍스트 로딩

작업 시작 시 다음 순서로 필요한 컨텍스트만 읽는다.

```text
프로젝트 CLAUDE.md
→ 현재 작업의 루트 기준 문서
→ 관련 상세 문서
→ 직접 관련된 상위 문서 구간
→ 필요한 경우에만 영향 문서
```

다음 원칙을 따른다.

- `docs/`와 상세 문서 디렉터리 전체를 일괄해서 읽지 않는다.
- 루트 기준 문서가 인덱스 역할을 하면 관련 상세 문서만 선택해서 읽는다.
- 상위 문서도 현재 작업과 직접 관련된 구간만 확인한다.
- 공통 규칙, 스킬 규칙과 프로젝트 상세 정보를 서로 중복해서 작성하지 않는다.
- 이미 읽은 정보라도 최신 상태 확인이 필요한 경우에만 다시 읽는다.
- 파일명만으로 책임을 추측하지 않고 루트 문서의 범위 설명을 우선 확인한다.

## 기준 문서 관리

작은 기준 문서는 단일 파일로 유지한다.

문서가 커져 선택적 로딩이 어려워진 경우에만 루트 문서를 인덱스로 전환하고 상세 문서를 분리할 수 있다.

```text
루트 기준 문서
→ 전체 기준, 공통 원칙, 상세 문서 인덱스

상세 문서
→ 기능, 도메인, 기술 관심사, 사용자 흐름 또는 구현 영역별 상세 내용
```

문서를 분리할 때 다음을 따른다.

- 사용자의 요청 없이 기존 문서 전체를 한 번에 분리하지 않는다.
- 새 상세 문서를 만들거나 이동·삭제하면 루트 인덱스를 함께 갱신한다.
- 같은 정책, 계약 또는 규칙을 여러 문서에서 원천처럼 중복 정의하지 않는다.
- 상세 문서의 범위와 로딩 조건은 간결하게 작성한다.
- 관련 없는 상세 문서는 읽거나 수정하지 않는다.

문서별 구체적인 분리 기준과 출력 경로는 각 설계 스킬을 따른다.

## 작업 기준

- 상위 문서에서 확정된 결정을 하위 문서에서 임의로 변경하지 않는다.
- 문서 간 충돌이나 기술적으로 불가능한 결정은 우회하지 않고 먼저 보고한다.
- 확정되지 않은 내용을 추측으로 결정하지 않는다.
- 기존 문서는 요청과 관련된 최소 범위만 수정한다.
- 기존 문서의 구조와 표현은 특별한 이유가 없으면 유지한다.
- 중요한 결정 변경은 원천 문서를 먼저 수정하고 결정 기록 문서에 반영할 대상인지 확인한다.
- 저장 전에 대상 문서가 작업 도중 변경되지 않았는지 확인한다.
- 수정 후 루트 인덱스, 상세 문서와 관련 기준 문서의 정합성을 검증한다.

## 금지 사항

- 모든 프로젝트 문서와 전역 스킬을 작업마다 일괄 로드
- 루트 문서와 상세 문서에 같은 내용을 반복 기록
- 하위 문서에서 제품 정책이나 상위 설계를 새로 결정
- 요청과 무관한 문서 분리, 재작성 또는 대량 포맷팅
- 존재하지 않는 문서, 코드 또는 명령을 실제 기준처럼 기록
- 검증하지 않은 작업을 완료했다고 보고
