# psw-implement

메인 세션이 오케스트레이터로 FR 단위 구현을 조율한다. 진행 방식은 FR마다 둘 중 하나다 (harness-psw 9.1, 9.2).

- 절충안(기본): 메인이 계약·AC 테스트·구현·직접 확인을 하고, 끝에 `reviewer`가 한 번 본다
- 전체 절차: `implementer`·`verifier`·`reviewer`를 나눈다. 메인은 직접 구현하지 않는다

## 전제 (구현 착수 조건)

- 대상 FR 파일과 관련 설계 문서가 `approved`다
- 용어집이 비어 있지 않다 (`.claude/scripts/psw/loop-status.sh`에 용어집 오류가 없다)
- 프로젝트별 결정이 채워져 있다 (`psw-design` 1·3·7단계)
  - `docs/design/conventions.md` 도구 절과 AC 테스트 절, `CLAUDE.md` 명령 표
  - `.claude/psw.conf`의 테스트 경로 패턴
  - 커밋 검사 hook 설정
- `dev` 브랜치가 있다. 없으면 사용자에게 `main`에서 만들지 묻는다
- 하위 에이전트 `implementer`, `reviewer`, `verifier`가 `.claude/agents/`에 있다
- `.claude/settings.json`에 `guard-paths.sh` hook이 있다 (`psw-init`)

하나라도 없으면 멈추고 사용자에게 알린다.

## 규칙

- FR은 한 번에 하나씩 진행한다
- FR 1개 = 기능 브랜치 1개: `dev`에서 `git switch -c feat/<FR-ID>-<요약> dev`
  - git worktree는 규칙이 아니다. 사용자가 원하면 써도 된다
- 테이블·API 문서는 없다. 계약(API 경로, 요청·응답 형식, 오류 코드, DB 마이그레이션)을 코드로 먼저 쓰고, 테스트는 확정된 계약으로 쓴다 (harness-psw 4.2, 9.2)
- 검토자·검증자에게 구현한 쪽(구현자 또는 메인)의 설명을 넘기지 않는다. 산출물과 원천 문서만 넘긴다
- 지적하는 쪽은 고치지 않는다. 수정은 구현한 쪽이 한다
- 절충안의 메인도 구현자 제한을 지킨다: 테마 파일·UI 컴포넌트 코드·`infra/`를 고치지 않고, 마이그레이션은 새 파일만 더한다. hook은 메인을 막지 않으므로 검토자가 diff로 확인한다
- 테스트를 통과시키려고 테스트를 고치지 않는다. 요구가 바뀐 것이면 문서 변경으로 모은다
- 같은 AC가 3회 FAIL하면 멈추고 사용자에게 보고한다 (설계·요구사항 문제로 본다)
- 같은 검토 지적(같은 근거·위치)이 2회 다시 나오거나 코드 검토가 3회차에도 CHANGES면 멈추고 사용자에게 보고한다
- 이어 쓰기: 한 FR 안에서는 같은 `implementer`·`verifier`·`reviewer`를 SendMessage로 이어 쓴다. 후속 지시(검토 지적, 검증 실패)는 묶어서 한 번에 보낸다. FR이 바뀌면 새로 부른다
  - 이어 쓸 수 없는 환경이면 새로 부르고, 지난 회차의 지적·실패를 함께 넘긴다
- 병렬 (전체 절차): 5단계 6(코드 검토 ∥ 테스트 실행)은 두 에이전트를 함께 돌린다. 둘 다 그 단계에서 같은 파일을 고치지 않는다. 계약 검토와 테스트 작성은 함께 돌리지 않는다 (계약을 확정한 뒤 테스트)
- 구현 중 문서 빈틈 (harness-psw 9.2 문서 변경 모으기). 구현자·검증자·검토자의 "상위 결함" 보고도 같다
  - 결정은 그때 사용자에게 받는다. 선택지·추천안을 함께 보인다
  - 받은 결정은 문서에 바로 쓰지 않고 목록으로 모은다: 결정, 바꿀 문서와 위치, 이 FR에서 반영한 코드
  - 병합 직전(6단계)에 `dev`에서 한 번에 반영하고 한 번 승인받는다 (`psw-loop`, 브랜치 이동은 `psw-loop` G)
  - 결정이 다른 FR의 범위를 바꾸면(새 테이블, 겹치는 범위) 모으지 않고 흐름을 멈추고 바로 `psw-loop`로 상위 루프를 호출한다
  - 설계 결함(코드 규칙, 테마·UI 컴포넌트 변경 포함) → 설계 루프 (`psw-design`), 요구사항 결함 → 기획 루프
- 원격(`origin`)이 있으면 (harness-psw 5.1)
  - 기능 브랜치는 첫 커밋 뒤 `git push -u origin feat/<FR-ID>-<요약>`로 올리고, 커밋할 때마다(하위 에이전트가 커밋을 보고할 때마다) 오케스트레이터가 push한다. 하위 에이전트는 push하지 않는다
  - `dev` push는 병합 확인(8단계)에서 함께 묻는다
  - 기능 브랜치는 `psw-loop` G의 rebase 뒤에만 `git push --force-with-lease`로 덮어쓴다. `main`·`dev`에는 force push하지 않는다
- 검사 범위 (harness-psw 9.2)
  - 반복 중에는 바꾼 부분과 관련된 검사·테스트만 돌린다 (이 FR의 AC 테스트, 바뀐 모듈의 lint). `CLAUDE.md` 명령 표의 "하나만 실행" 명령을 쓴다
  - 전체 검사(빌드, 전체 테스트)는 구현 완료 직전과 판정(절충안은 검토자 호출) 직전에 한 번씩 돌린다. 도구 검사는 한 번 돌린다
  - 하위 에이전트를 호출할 때 이 범위를 함께 알린다
- MUST: `dev`로 합치기 전에 FR마다 사용자 확인을 받는다
- 병합은 개별 커밋을 유지한다. squash하지 않는다
- NEVER: `main`에 커밋하거나 합치지 않는다. 배포는 사용자가 한다
- 구현 중에는 같은 작업 폴더에서 다른 세션이 git 작업을 하지 않게 한다. 다른 세션 작업이 필요하면 별도 worktree에서 하도록 사용자에게 알린다 (harness-psw 5.1)

## 준비 (프로젝트에서 처음 한 번)

1. 커밋 검사 도구가 harness 스크립트로 정해졌으면
   - `templates/githooks/commit-msg`를 `.githooks/commit-msg`로 복사한다
   - `git config core.hooksPath .githooks`
   - 다른 도구(commitlint 등)로 정했으면 그 도구 설정에서 `check-commit-msg.sh`와 같은 규칙을 적용한다
2. 시크릿 스캔 도구가 gitleaks로 정해졌으면
   - `gitleaks version`으로 설치를 확인한다. 없으면 멈추고 사용자에게 설치를 요청한다. 설치를 대신하지 않는다
   - `templates/githooks/pre-commit`을 `.githooks/pre-commit`으로 복사한다 (위의 `core.hooksPath`를 함께 쓴다)
   - 확인: 가짜 키를 넣은 파일을 스테이징하고 커밋이 막히는지 본 뒤, 그 파일은 스테이징을 풀고 지운다
   - 다른 도구로 정했으면 그 도구의 pre-commit 연결 방법을 따른다
3. GitHub를 쓰면 `templates/github-workflow-psw.yml`을 `.github/workflows/psw.yml`로 복사할지 사용자에게 묻는다
4. 프론트가 있으면 프론트 CI(lint, 타입, 빌드, 공통 넘침 테스트)와 공통 넘침 테스트를 둘지 묻는다. 워크플로 예시와 테스트 틀은 프론트 키트 `web/frameworks/<프레임워크>/README.md`에 있다
   - 공통 넘침 테스트 파일이 `.claude/psw.conf`의 `PSW_TEST_GLOBS`에 들어 있는지 확인한다

## FR 흐름

### 1. 묶음 고르기

- `approved` FR 중 의존 순서가 앞선 것 몇 개(예: 같은 도메인의 앞선 FR 3~5개)를 묶음으로 고른다 (`.claude/scripts/psw/rtm.sh`로 현황 확인)
- 묶음과 순서를 사용자에게 보이고 확인받는다

### 2. 착수 점검 (검토자, 묶음 단위)

기능 브랜치를 만들기 전에 `dev`에서 한다. 문서를 고쳐도 브랜치를 옮길 일이 없다.

- `reviewer`를 "착수 점검"으로 호출한다. 넘길 것: 묶음의 FR 경로들, 관련 `_policy.md`·화면 경로(`find-refs.sh <FR-ID>`), FR `refs`의 영역 문서
- 묶음의 질문을 모아 한 번에 사용자에게 묻는다. 선택지와 추천안을 함께 보인다
  - 답은 `psw-loop`로 원천 문서에 반영하고 한 번에 승인받는다
  - 정하지 않고 진행하기로 하면 미결 보류로 등록한다 (`psw-loop` C)
- 크기 신호가 있으면 분리 조건(harness-psw 3.4)에 맞는지 보이고, 나눌지 사용자에게 묻는다. 나누면 기획 루프(`psw-req` 갱신)로 넘긴다
- FR마다 진행 방식을 정한다. 기본은 절충안이다. 검토자가 낸 신호(`SEC-` 참조, 인증·권한·개인정보, 크기 신호)가 있으면 전체 절차를 권하고 사용자가 확정한다
- 점검이 끝나면 묶음의 첫 FR부터 3단계로 간다

### 3. 기능 브랜치

- `dev`에서 `git switch -c feat/<FR-ID>-<요약> dev`
- 원격이 있으면 첫 커밋(계약 또는 테스트) 뒤 원격에 올린다
- 진행 방식에 따라 4(절충안) 또는 5(전체 절차)로 간다

### 4. 절충안 (메인)

1. 계약: 서버 쪽 변경이 있으면 `docs/design/conventions.md` REST·DB 절을 따라 컨트롤러 시그니처, 요청·응답 형식, 새 오류 코드, DB 마이그레이션을 쓰고 동작은 비워 둔다. 커밋 `feat: <제목> 계약`
2. AC 테스트: FR의 AC를 성격별로 나눠 백엔드(API·데이터·상태 전이) AC 테스트를 쓴다. 작성법은 `conventions.md` AC 테스트 절, 위치는 `architecture.md` 백엔드 절. 이 FR의 테스트만 돌려 아직 실패하는지 본다. 커밋 `test: <제목>`
   - 화면 AC는 테스트를 쓰지 않는다. 새 화면이 생기면 공통 넘침 테스트에 경로를 더한다
3. 구현: 테스트를 통과시킨다. 커밋 `feat: <제목>`
4. 도구 검사: lint·타입 검사, 전체 테스트 (`CLAUDE.md` 명령)
5. 화면 AC 직접 확인: 앱을 띄워 브라우저로 AC마다 확인하고 스크린샷을 남긴다(커밋하지 않는다). 새 화면이면 공통 넘침 테스트를 돌린다
6. 독립 검토: `git diff dev...feat/<FR-ID>-<요약>`을 뽑아 `reviewer`를 "코드 검토 (절충안)"로 호출한다. 넘길 것: diff 전문, FR 경로, 관련 `_policy.md`·화면 경로. 메인의 설명은 넘기지 않는다
   - CHANGES면 고치고 4~5를 다시 한다. 높음 지적을 고쳤으면 고친 diff만 다시 보게 한다 (회차 상한은 규칙과 같다)
7. 6단계로 간다

### 5. 전체 절차 (하위 에이전트)

1. 계약 (구현자): 서버 쪽 변경이 없는 FR이면 건너뛴다. `implementer`를 "계약" 단계로 호출한다. 넘길 것: 기능 브랜치, FR 경로, 관련 `_policy.md` 경로
2. 계약 검토 (검토자): `reviewer`를 "계약 검토"로 호출한다. 넘길 것: 계약 커밋의 diff, FR 경로, 관련 `_policy.md` 경로
   - 서버 변경이 작으면(새 경로 1개 이하, 새 테이블 없음) 건너뛰고 코드 검토에서 함께 본다
   - 지적이 있으면 구현자에게 넘겨 계약을 고친 뒤 3으로 간다. 테스트를 쓰기 전에 계약을 확정한다
3. AC 테스트 작성 (검증자): `verifier`를 "테스트 작성" 단계로 호출한다. 넘길 것: 기능 브랜치, FR 경로, 관련 `_policy.md`·화면 경로(`find-refs.sh <FR-ID>`), 확정된 계약 커밋
4. 구현 (구현자): `implementer`를 "구현" 단계로 호출한다 (계약을 쓴 구현자를 이어 쓴다). 넘길 것: 기능 브랜치, FR 경로, 관련 `_policy.md`·화면 경로, 이전 반복의 지적·실패(묶어서 한 번에)
   - "중단" 보고면 사유에 따라 규칙대로 처리한다
5. 도구 검사: lint·타입 검사를 한 번 돌린다. 실패하면 4로 돌아간다
6. 코드 검토 (검토자) ∥ 테스트 실행 (검증자)
   - diff를 뽑는다: `git diff dev...feat/<FR-ID>-<요약>`
   - `reviewer`를 "코드 검토"로 호출한다. 넘길 것: diff 전문, FR 경로, 관련 `_policy.md`·화면 경로
   - 같은 때 `verifier`에게 이 FR의 AC 테스트만 실행해 결과를 알려 달라고 한다. 판정이 아니다
   - CHANGES이거나 실패한 테스트가 있으면 지적과 실패를 묶어 구현자에게 넘겨 4로 돌아간다
   - 다시 검토할 때는 diff 전문과 지난 회차 지적 표를 함께 넘긴다. 지적 번호(N1, N2, …)는 회차를 넘어 이어 쓴다
7. 검증 (검증자): `verifier`를 "검증" 단계로 호출한다. FAIL이면 실패 AC를 구현자에게 넘겨 4로 돌아간다. AC별 FAIL 횟수를 센다
8. 6단계로 간다

### 6. 문서 변경 반영 (모은 것이 있을 때)

- 모은 결정을 `dev`에서 원천 문서에 한 번에 반영하고 승인을 요청한다 (`psw-loop`, 브랜치 이동은 `psw-loop` G)
- 승인 뒤 기능 브랜치를 `dev`로 rebase하고, 원격이 있으면 `git push --force-with-lease`
- rebase로 코드가 바뀌었으면 이 FR의 AC 테스트를 다시 돌린다

### 7. 커밋 검사

- 브랜치의 각 커밋: `.claude/scripts/psw/check-commit-msg.sh --commit <커밋>` (`git rev-list dev..feat/<FR-ID>-<요약>`)
- 실패하면 원인을 고친다

### 8. 사용자 확인

아래 형식으로 요청한다. 전체 절차면 AC 결과는 검증자 보고를 그대로 옮긴다. 직접 확인한 화면 AC는 스크린샷을 함께 보인다.

```text
[병합 확인] <FR-ID> <제목>
- 진행 방식: 절충안 / 전체 절차
- 변경 파일: N개 (코드 n, 테스트 n)
- AC 결과: AC-1 PASS(테스트) / AC-2 PASS(직접 확인, 스크린샷) / AC-3 FAIL [SHOULD] 사유: ...
- 검토 지적: N건 → 처리 결과
- 문서 변경: <없음 또는 반영·재승인한 결정 수와 문서>
- 남은 미결: <없음 또는 목록>
→ dev에 합치고 origin에 올릴까요?
```

- 원격이 없으면 마지막 줄은 `→ dev에 합칠까요?`로 묻는다

### 9. 병합과 정리

1. `dev`로 합친다: `git switch dev` 후 `git merge feat/<FR-ID>-<요약>`
2. 원격이 있으면 `git push origin dev`. 그 사이 쌓인 문서 커밋도 함께 올라가고, CI가 돈다
3. 기능 브랜치를 지운다
   - 원격: `git push origin --delete feat/<FR-ID>-<요약>` (`dev` push가 끝난 뒤)
   - 로컬: `git branch -d feat/<FR-ID>-<요약>`
4. 병합으로 바뀐 코드가 다른 FR에 영향을 주는지 `find-refs.sh`로 찾고, 영향받은 FR의 직접 확인 AC를 다시 확인한다
   → AC 테스트 코드가 있는 AC는 테스트 실행·CI가 다시 확인한다
5. 묶음에 다음 FR이 있으면 3단계로 간다. 묶음이 끝나면 1단계로 간다
