# psw-crosscheck

설계 문서끼리, 그리고 요구사항과 어긋난 곳을 찾는다. 이 스킬은 고치지 않고 찾기만 한다.

## 검증 항목

| # | 항목 | 방식 |
|---|---|---|
| 1 | 승인된 FR이 화면 또는 API에서 참조된다 | 스크립트 |
| 2 | NFR·SEC·INT가 설계 문서에서 참조된다 | 스크립트 |
| 3 | 목업 메타의 API ID가 API 문서에 있다 | 스크립트 |
| 4 | API 요청·응답 필드가 ERD 컬럼과 대응한다 (파생 필드는 명시) | 검토자 |
| 5 | API가 유발하는 상태 전이가 state 전이 표에 있고, 사용자 이벤트마다 대응 API가 있다 | 검토자 |
| 6 | API 허용 역할과 IA 접근 역할이 `docs/req/actors.md`와 일치한다 | 검토자 |
| 7 | state 문서마다 ERD가 참조한다 | 스크립트 |
| 8 | 목업의 `data-component` 값이 `components.md`에 있다 | 스크립트 |
| 9 | 연동 실패 처리가 API 오류나 상태 전이에 반영돼 있다 | 검토자 |
| 10 | 화면·API의 refs가 비어 있지 않다 | 스크립트 |
| 11 | 쓰이지 않는 테이블·API (경고) | 스크립트 |
| 12 | 참조한 ID가 정의돼 있다 | 스크립트 |

## 절차

### 1. 스크립트 항목

- `.claude/scripts/psw/crosscheck.sh [도메인 코드]`를 실행한다
  - 도메인 코드를 주면 항목 1, 3, 10, 12를 그 도메인으로 좁힌다. 나머지는 전역으로 본다
  - 스크립트 항목은 싸므로 매번 전체를 실행한다

### 2. 검토자 항목 (4, 5, 6, 9)

- 검토자 에이전트(`reviewer`)가 설치돼 있으면 맡긴다. 없으면 메인 세션이 확인하고, 그 사실을 결과에 적는다
- 검토자에게 넘기는 것: 대상 도메인의 설계 문서 경로, `docs/req/actors.md`, 관련 FR 파일 경로
  - 설계 작성자의 설명은 넘기지 않는다
- 반복 실행이면 영향받은 문서만 다시 본다 (`psw-change` 절차 F의 영향 경로)
- 지적마다 근거 ID와 위치(파일, 제목)를 단다. 근거가 없으면 "제안"으로 분류한다

### 3. 결과 정리

| 결과 | 처리 |
|---|---|
| 설계 문제 | `psw-design`으로 `draft`에서 고친다 |
| 요구사항 문제 | `psw-change`로 기획 루프를 호출한다 |
| 근거가 빈 설계 요소 | 범위 밖 작업을 의심하고 사용자에게 확인한다 |
| 경고 (항목 11) | 의도한 것이면 무시한다 (예: 서버 전용 API) |

- 같은 불일치가 2회 이상 다시 나오면 요구사항 문제로 보고 사용자에게 보고한다
- 결과 보고: 항목별 오류·경고 수, 지적 목록, 처리 방향
