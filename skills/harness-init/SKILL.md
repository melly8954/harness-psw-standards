# Harness Init

프로젝트 에이전트 지시서는 프로젝트의 모든 세부 지식을 담는 문서가 아니다. 상세 요구사항, 설계, API, 데이터 모델, 정책은 각 책임 위치에 두고, 지시서는 에이전트가 어떻게 행동하고 필요한 정보를 어디에서 찾는지 안내하는 경량 진입점으로 만든다.

최상위 지시서는 프로젝트 루트의 `AGENTS.md`, `CLAUDE.md` 등 실제 사용하는 파일만 대상으로 한다. 모든 프로젝트에 같은 파일이나 같은 섹션을 강제하지 않는다.

## 작성 원칙

- 현재 프로젝트의 구조와 실제 존재하는 문서를 기준으로만 내용을 구체화한다.
- 프로젝트 성격·규모·기술 스택·운영 방식에 맞는 섹션만 선택한다.
- 확인되지 않은 제품·비즈니스 정책을 만들지 않는다.
- 특정 에이전트에만 해당하는 동작은 공통 규칙과 구분한다.
- 지시서는 작고 안정적으로 유지하며, 상세 문서를 그대로 복제하지 않는다.

## 실행 순서

한 번의 하네스 구축에서는 아래 단계를 순서대로 수행한다. 각 단계의 사실 목록, 포함·생략 결정, 초안, 확인 필요 사항을 다음 단계에 전달한다.

1. `harness-scan` — 프로젝트 사실과 근거 수집
2. `harness-scope` — 프로젝트 목적과 책임 경계 작성
3. `harness-routing` — 문서 지도와 탐색 규칙 작성
4. `harness-principles` — 공통 작업 원칙 작성
5. `harness-implementation` — 구현 규칙 진입점 작성
6. `harness-verification` — 검증·QA 기준 작성
7. `harness-operations` — 실행·배포·운영 경계 작성
8. `harness-git` — 기존 변경 보존, 충돌 방지, 커밋·브랜치·PR 원칙 작성
9. `harness-secrets` — 환경 변수·시크릿 원칙 작성
10. `harness-compose` — 선택된 섹션 조립과 사실성 검증

`harness-principles`, `harness-git`, `harness-secrets`의 안전 규칙은 자기 차례뿐 아니라 전체 과정에 적용한다. 개별 `harness-*` 스킬은 특정 섹션만 다시 검토하거나 갱신할 때 직접 사용하며, 그 경우 해당 스킬의 `확인 필요` 항목만 사용자에게 직접 질문한다.

## 판단과 인터뷰

각 단계는 `사실`, `근거`, `지시서 반영`, `생략`, `확인 필요`를 남긴다. 근거가 있는 내용은 초안에 반영하고, 근거가 없더라도 선택하지 않아도 안전한 내용은 생략한다.

프로젝트 작업 방식이나 권한에 실질적인 영향을 주는 미확인·충돌 항목만 모아, 초안 조립 전에 한 번에 사용자에게 질문한다. 단계마다 질문을 반복하지 않으며, 확인되지 않은 정책을 새로 정하지 않는다.

## 반영 규칙

조사와 초안 작성 중에는 대상 프로젝트 파일을 수정하지 않는다. `harness-compose`가 근거와 확인 필요 사항을 포함한 초안을 먼저 제시하고, 사용자가 명시적으로 반영을 요청한 경우에만 실제 지시서를 수정한다.
