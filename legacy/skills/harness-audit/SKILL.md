# Harness Audit

전역 하네스와 프로젝트 문서 구조의 일관성, 책임 경계와 컨텍스트 효율을 검증한다.

## 공통 규칙

작업 전에 다음 문서를 읽고 따른다.

- `~/.claude/harness/common-execution-rules.md`
- `~/.claude/harness/harness-structure.md`

## 입력

1. 프로젝트 `CLAUDE.md`
2. 감사 대상 루트 문서
3. 감사 대상과 관련된 상세 문서
4. 관련된 `docs/decisions.md` 또는 개별 결정 기록
5. 전역 스킬 구조
6. 사용자 지정 감사 범위

전체 감사를 요청받지 않았다면 관련 루트 문서와 상세 문서만 검사한다.

상세 디렉터리 전체 검사가 필요한 경우에도 먼저 루트 인덱스로 검사 범위를 식별한다.

## 감사 모드

- 구조 감사: 경로, 파일명, 인덱스, 참조와 책임 배치를 점검한다.
- 문서 감사: 문서 간 충돌, 누락, 중복과 추적 가능성을 점검한다.
- 컨텍스트 감사: 불필요한 로딩, 과도한 분리와 중복 규칙을 점검한다.
- 변경 감사: 특정 변경이 관련 문서와 인덱스에 반영되었는지 점검한다.
- 전체 감사: 위 항목을 모두 수행한다.

## 감사 절차

1. 요청 범위와 원천 기준 문서를 확정한다.
2. 프로젝트 문서 구조와 선택 로딩 규칙을 확인한다.
3. 루트 인덱스와 실제 상세 문서 경로를 비교한다.
4. 상위 문서에서 하위 문서로 핵심 결정을 추적한다.
5. 용어, 역할, 상태, 코드 값과 정책을 비교한다.
6. 문서별 책임 경계와 중복 정의를 확인한다.
7. `decisions` 기록과 현재 유효한 설계 결정을 비교한다.
8. 과다 로딩, 과도한 분리와 지나치게 큰 단일 문서를 검사한다.
9. 문제를 심각도, 원천 원인과 수정 순서로 분류한다.
10. 자동 수정 가능한 구조 문제와 사용자 결정이 필요한 문제를 구분한다.
11. 감사 결과와 권장 수정 순서를 보고한다.

## 감사 기준

### 구조

- 필요한 루트 문서와 스킬 경로가 존재하는가
- 루트 인덱스에 등록된 상세 문서가 실제로 존재하는가
- 실제 상세 문서가 루트 인덱스에서 누락되지 않았는가
- 파일명, 대소문자와 참조 경로가 일치하는가
- 같은 문서가 중복 등록되지 않았는가
- 프로젝트 `CLAUDE.md`가 실제 문서 경로를 사용하고 있는가
- 프로젝트 `CLAUDE.md`가 전역 규칙을 불필요하게 복사하지 않는가

### 문서 책임

- 제품 목표와 범위가 PRD를 기준으로 유지되는가
- Architecture가 시스템 경계와 기술 관심사를 담당하는가
- ERD가 데이터 관계, 상태와 제약을 담당하는가
- API가 공개 계약만 정의하는가
- App Design이 화면 흐름과 UI 상태를 담당하는가
- Coding Convention이 상위 설계를 변경하지 않는가
- Decisions가 이미 확정된 결정과 대체 관계만 기록하는가
- 공통 내용이 상세 문서마다 반복되지 않는가
- 하나의 정책이나 계약이 여러 문서에서 원천처럼 정의되지 않는가

### 문서 일관성

- Architecture가 PRD 요구를 지원하는가
- ERD가 제품 정책과 데이터 정합성 요구를 표현하는가
- API가 ERD와 상태·필드 의미를 공유하는가
- App Design이 PRD와 API 흐름에 맞는가
- Coding Convention이 실제 설계를 일관되게 구현하도록 하는가
- Decisions가 현재 결정과 대체 관계를 반영하는가
- 루트 문서의 요약과 상세 문서의 실제 내용이 충돌하지 않는가

### 컨텍스트 효율

- 모든 작업에서 `docs/` 전체를 읽도록 강제하지 않는가
- 상세 디렉터리 전체를 항상 읽도록 지시하지 않는가
- 루트 문서만 읽고 관련 상세 문서를 찾을 수 있는가
- 상세 문서의 범위와 로딩 조건이 명확한가
- 긴 예시와 예외가 항상 로드되는 위치에 있지 않은가
- 스킬 설명과 호출 조건이 과도하게 길지 않은가
- 작은 문서가 불필요하게 여러 파일로 분리되지 않았는가
- 큰 문서가 선택적 로딩이 불가능한 상태로 남아 있지 않은가
- 현재 작업과 무관한 문서 의존이 없는가

```

같은 원인에서 발생한 여러 증상은 하나의 발견으로 묶을 수 있다.

## 심각도

- Critical: 구현 불가능, 보안·정합성 훼손 또는 기준 문서 직접 충돌
- High: 핵심 정책, 구조, 데이터 또는 공개 계약의 불일치
- Medium: 특정 기능 누락, 인덱스 불일치, 책임 경계 침범 또는 큰 유지보수 위험
- Low: 명명, 경로, 경미한 중복, 과도한 분리와 컨텍스트 효율 문제

심각도는 프로젝트 영향, 전파 범위와 수정 비용을 근거로 판단한다.

단순 취향 차이는 결함으로 보고하지 않는다.

## 수정 원칙

- 감사 중 설계 결정을 임의로 변경하지 않는다.
- 오타, 깨진 경로와 명백한 인덱스 누락처럼 의미가 변하지 않는 수정만 자동 적용할 수 있다.
- 자동 수정도 사용자가 감사만 요청한 경우에는 적용하지 않고 가능 항목으로 보고한다.
- 정책, 구조, 데이터와 API 의미가 바뀌는 수정은 문제와 권장안만 보고한다.
- 여러 문제가 연결되면 가장 상위의 원천 문서부터 수정하도록 순서를 제시한다.
- 과도한 분리와 큰 단일 문서 문제는 실제 로딩 비용과 변경 범위를 근거로 판단한다.

## 출력

- 감사 범위와 검사한 기준
- 심각도별 문제 목록
- 문제 유형
- 문제의 위치, 근거, 영향과 권장 수정
- 루트 인덱스와 상세 문서 상태
- 문서별 상태
- 권장 수정 순서
- 자동 수정 가능 항목
- 사용자 결정 필요 항목

설계 의미가 바뀌는 수정은 사용자 승인 없이 적용하지 않는다.

```

문제가 없으면 검사 범위와 통과한 기준을 명시한다.

## 완료 검증

- 요청한 감사 범위를 모두 검사했는가
- 루트 인덱스와 실제 상세 문서를 비교했는가
- 문제마다 위치, 근거와 영향이 있는가
- 단순 취향을 결함처럼 보고하지 않았는가
- 상위 원인과 하위 증상을 구분했는가
- 심각도와 수정 순서가 일관적인가
- 자동 수정과 사용자 결정 항목을 구분했는가
- 감사 과정에서 설계 결정을 임의로 변경하지 않았는가
- 책임 중복, 인덱스 불일치와 과다 로딩을 확인했는가
- 과도한 분리와 지나치게 큰 문서를 함께 확인했는가
