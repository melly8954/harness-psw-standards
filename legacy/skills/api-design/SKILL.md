# API Design

클라이언트와 서버 사이의 계약을 `docs/API.md`와 `docs/api/` 하위 문서에 정리한다.

```text
docs/
├─ API.md
└─ api/
   ├─ common.md
   └─ <domain>.md
```

- `docs/API.md`: 전체 API 문서의 인덱스와 도메인별 문서 경로
- `docs/api/common.md`: 공통 요청·응답, 인증, 오류와 페이지네이션 규칙
- `docs/api/<domain>.md`: 도메인별 API 계약

## 공통 규칙

작업 전에 `~/.claude/harness/common-execution-rules.md`를 읽고 따른다.

## 입력

필요한 항목만 선택해서 읽는다.

1. 프로젝트 `CLAUDE.md`
2. 사용자 요청
3. 관련된 `docs/prd.md` 구간
4. 관련된 `docs/prd/<feature>.md`
5. 관련된 `docs/Architecture.md` 구간
6. 관련된 `docs/architecture/<concern>.md`
7. 관련된 `docs/ERD.md` 구간
8. 관련된 `docs/erd/<domain>.md`
9. `docs/API.md`
10. `docs/api/common.md`
11. 요청과 관련된 `docs/api/<domain>.md`
12. 관련된 `docs/decisions.md` 항목
13. 요청에서 직접 참조한 자료

`docs/api/` 전체를 일괄해서 읽지 않는다.

`app-design.md`는 화면 흐름 또는 클라이언트 상태와의 정합성을 확인할 때만 읽는다.

기존 `docs/API.md`가 단일 문서라면 요청과 관련된 범위만 확인한다. 사용자의 요청 없이 전체를 한 번에 분리하거나 재작성하지 않는다.

## 문서 분류

- 전체 API 목록과 문서 탐색 정보: `docs/API.md`
- 여러 도메인에 공통으로 적용되는 계약: `docs/api/common.md`
- 특정 도메인의 엔드포인트와 동작 계약: `docs/api/<domain>.md`

도메인은 비즈니스 책임과 권한 경계를 기준으로 분류한다.

패키지명, 컨트롤러명 또는 테이블명을 그대로 문서 경계로 사용하지 않는다.

한 API가 여러 도메인과 연관되더라도 주 책임 도메인 문서 한 곳에 정의하고 다른 문서에서는 참조한다.

새 도메인 문서를 생성하거나 경로를 변경하면 `docs/API.md`를 갱신한다.

파일명은 소문자 kebab-case를 기본으로 한다.

```text
auth.md
users.md
workspaces.md
workspace-members.md
channels.md
messages.md
files.md
realtime.md
```

## 문서 분리 기준

기본적으로 하나의 도메인은 하나의 문서로 관리한다.

다음 조건에서는 하위 문서 분리를 검토한다.

- 필요한 계약만 선택해서 읽기 어려울 정도로 문서가 커짐
- 조회와 명령의 변경 범위가 명확히 다름
- 파일·실시간·외부 연동 계약이 독립적으로 큼
- 서로 다른 작업이 같은 문서를 반복해서 수정함

```text
docs/api/messages/
├─ README.md
├─ commands.md
├─ queries.md
└─ realtime.md
```

작은 도메인을 처음부터 여러 파일로 나누지 않는다.

## 작업 모드

- 생성: 필요한 인덱스, 공통 계약 또는 도메인 문서를 생성한다.
- 수정: 요청과 관련된 API 계약과 필요한 인덱스만 변경한다.
- 검증: 일관성, 보안, 오류, 정합성과 구현 가능성을 점검한다.
- 분리: 사용자가 요청하거나 현재 문서 규모상 필요한 경우 기존 계약을 분리한다.

사용자가 명시하지 않아도 필요한 모드를 판단해 수행한다.

기존 단일 `docs/API.md`를 분리할 때는 내용을 삭제하거나 새로 해석하지 않는다. 원래 의미대로 이동하고 `docs/API.md`는 인덱스로 전환한다.

## 설계 절차

1. 사용자 행위와 시스템 책임을 API 작업 단위로 분리한다.
2. API의 주 책임 도메인과 수정할 문서를 결정한다.
3. 리소스, 명령과 조회 경계를 정한다.
4. 경로, 메서드와 인증 요구사항을 정의한다.
5. 요청 데이터, 검증 조건과 기본 동작을 정리한다.
6. 응답 데이터와 상태 코드를 정의한다.
7. 도메인 오류와 공통 오류 형식을 정리한다.
8. 권한, 소유권과 데이터 노출 범위를 확인한다.
9. 멱등성, 중복 요청, 동시성과 재시도 영향을 검토한다.
10. 목록 조회의 필터, 정렬과 페이지네이션을 정의한다.
11. 공통 계약과 도메인 계약의 중복 여부를 확인한다.
12. 문서 인덱스, 변경 영향과 미확정 사항을 정리한다.

## API 고유 원칙

- API는 클라이언트와 서버 간 공개 계약으로 작성한다.
- 내부 클래스, 서비스 메서드와 저장소 구조를 그대로 노출하지 않는다.
- 동일한 의미에는 일관된 경로, 필드명과 오류 형식을 사용한다.
- 인증 여부와 역할·소유권 기반 인가를 구분한다.
- 요청 검증 실패와 비즈니스 규칙 위반을 구분한다.
- 성공·실패 상태 코드와 응답 의미가 일치해야 한다.
- 생성, 수정, 삭제의 중복 요청 처리 기준을 명시한다.
- 목록 API는 데이터 증가를 고려해 조회 조건을 정의한다.
- 민감정보와 내부 식별자 노출 필요성을 검토한다.
- 현재 요구에 없는 범용 API를 미리 추가하지 않는다.
- 공통 계약을 도메인 문서마다 반복해서 정의하지 않는다.
- 관련 없는 도메인 문서를 예방적으로 읽거나 수정하지 않는다.

## API 항목 기준

각 API에는 필요한 항목만 작성한다.

- 목적
- 인증과 권한
- 메서드와 경로
- 경로 변수
- 쿼리 파라미터
- 요청 헤더
- 요청 본문
- 필드 검증
- 성공 응답
- 오류 응답
- 상태 코드
- 멱등성
- 페이지네이션
- 정렬과 필터
- 부작용
- 관련 정책

공통 응답 형식이나 오류 형식은 `docs/api/common.md`에서 한 번만 정의한다.

도메인별 예외나 추가 규칙은 공통 계약과의 차이만 작성한다.

## 상태 변경 API

상태를 변경하는 API는 다음을 추가로 확인한다.

- 허용되는 이전 상태
- 변경 후 상태
- 실행 권한
- 중복 실행 결과
- 동시 요청 처리
- 실패 시 원자성
- 외부 연동 실패 처리
- 이벤트 또는 후속 작업

## 불확실성 처리

API 계약에 영향을 주는 정책이 미확정이면 다음을 제시한다.

- 확인이 필요한 정책
- 가능한 계약 선택지
- 클라이언트·서버·호환성 영향
- 권장안과 근거

확정 전에는 권장안을 최종 API 계약으로 기록하지 않는다.

PRD, Architecture 또는 ERD와 충돌하면 API만 변경해 우회하지 않고 기준 문서의 수정 필요성을 먼저 알린다.

## 출력

- API 인덱스: `docs/API.md`
- 공통 API 계약: `docs/api/common.md`
- 도메인 API 계약: `docs/api/<domain>.md`
- 기존 문서 수정 시 관련 API와 공통 계약만 변경한다.
- 새 문서를 만들거나 경로를 변경하면 `docs/API.md`를 갱신한다.
- 관련 없는 도메인 문서는 수정하지 않는다.
- 예시는 계약 이해에 필요한 최소 수준으로 작성한다.
- 주요 계약 변경은 `decisions-sync` 대상인지 판단한다.
- `app-design.md` 또는 `coding-convention.md` 재검토가 필요하면 대상과 이유를 알린다.

## 완료 검증

- 사용자 흐름과 API 작업 단위가 연결되는가
- API가 올바른 공통 또는 도메인 문서에 배치되었는가
- `docs/API.md` 인덱스와 실제 문서 경로가 일치하는가
- 공통 계약이 도메인 문서에 중복되어 있지 않은가
- 경로, 메서드와 리소스 의미가 일관적인가
- 인증과 인가 기준이 명확한가
- 요청 검증과 비즈니스 오류가 구분되는가
- 상태 코드와 응답 의미가 일치하는가
- 상태 변경과 동시성 기준이 설명되는가
- 목록 조회가 증가하는 데이터를 처리할 수 있는가
- 민감정보와 불필요한 내부 정보가 노출되지 않는가
- PRD, Architecture와 ERD의 의미가 충돌하지 않는가
- 내부 구현 세부사항을 계약으로 고정하지 않았는가
- 변경 영향이 있는 하위 문서를 식별했는가
