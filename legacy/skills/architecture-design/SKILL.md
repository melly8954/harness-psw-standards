# Architecture Design

시스템 구조를 `docs/Architecture.md`와 `docs/architecture/` 하위 문서에 정리한다.

```text
docs/
├─ Architecture.md
└─ architecture/
   └─ <concern>.md
```

- `docs/Architecture.md`: 전체 시스템 구조, 기술 원칙과 상세 문서 인덱스
- `docs/architecture/<concern>.md`: 인증, 실시간, 파일, 배포 등 기술 관심사별 설계

## 공통 규칙

작업 전에 `~/.claude/harness/common-execution-rules.md`를 읽고 따른다.

## 입력

필요한 항목만 선택해서 읽는다.

1. 프로젝트 `CLAUDE.md`
2. 사용자 요청
3. 관련된 `docs/prd.md` 구간
4. 관련된 `docs/prd/<feature>.md`
5. 기존 `docs/Architecture.md`
6. 요청과 관련된 `docs/architecture/<concern>.md`
7. 관련된 `docs/decisions.md` 항목
8. 요청에서 직접 참조한 자료
9. 실제 구현·배포 구조 확인이 필요한 경우 관련 코드와 설정

`docs/architecture/` 전체를 일괄해서 읽지 않는다.

ERD, API와 Coding Convention은 정합성 또는 변경 영향을 확인할 때만 읽는다.

## 문서 분류

다음 내용은 `docs/Architecture.md`에 유지한다.

- 시스템 목적과 설계 목표
- 전체 시스템 경계와 구성 요소
- 핵심 기술 원칙
- 주요 데이터·통신 흐름
- 공통 비기능 요구사항
- 기술 관심사 문서 인덱스
- 전체 배포·운영 개요

다음 내용은 `docs/architecture/<concern>.md`로 분리할 수 있다.

- authentication
- authorization
- realtime
- file-storage
- messaging
- deployment
- observability
- security
- external-integrations

Architecture는 비즈니스 도메인보다 기술 관심사를 기준으로 분리한다.

## 문서 분리 기준

기본적으로 작은 시스템은 `docs/Architecture.md` 하나로 유지한다.

다음 조건에서는 관심사별 분리를 검토한다.

- 한 기술 영역이 독립적인 흐름·위험·운영 정책을 가짐
- 관련 설계만 선택해서 읽기 어려울 정도로 문서가 커짐
- 배포, 인증, 실시간 등 변경 주기가 명확히 다름
- 여러 작업이 동일 문서를 반복해서 수정함

사용자의 요청 없이 기존 문서 전체를 한 번에 분리하지 않는다.

## 작업 모드

- 생성: 전체 구조와 필요한 관심사 문서를 작성한다.
- 수정: 요청과 관련된 기술 구조만 변경한다.
- 검증: PRD 충족, 시스템 경계, 보안, 운영성과 정합성을 점검한다.
- 분리: 문서 규모상 필요하거나 사용자가 요청한 경우 관심사별로 분리한다.

## 설계 절차

1. 관련 PRD 목표와 제약을 확인한다.
2. 시스템 경계와 외부 주체를 식별한다.
3. 주요 구성 요소와 책임을 정의한다.
4. 동기·비동기 통신과 데이터 흐름을 정리한다.
5. 인증, 인가, 저장, 실시간과 외부 연동 구조를 설계한다.
6. 배포, 확장, 장애, 보안과 관측성 요구를 검토한다.
7. 기술 선택의 근거와 대안을 정리한다.
8. 데이터 모델과 공개 API에 미치는 영향을 확인한다.
9. 공통 구조와 관심사 문서의 중복을 제거한다.
10. 미확정 사항과 변경 영향을 정리한다.

## Architecture 고유 원칙

- PRD의 목표와 제약을 만족하는 기술 구조를 정의한다.
- 구성 요소의 책임과 경계를 명확히 한다.
- 기술 선택에는 문제, 대안, 이유와 영향을 남긴다.
- 상세 테이블·컬럼, DTO와 화면 배치를 확정하지 않는다.
- 현재 요구에 없는 분산 시스템이나 외부 인프라를 미리 도입하지 않는다.
- 보안·운영·비용·복잡도 간 trade-off를 검토한다.
- 공통 기술 원칙을 관심사 문서마다 반복하지 않는다.
- 실제 구현이 문서와 다르다고 해서 구현을 자동으로 정답으로 간주하지 않는다.

## 관심사 문서 기준

각 관심사 문서에는 필요한 항목만 작성한다.

- 목적과 범위
- 관련 요구사항
- 구성 요소와 책임
- 처리 흐름
- 데이터와 상태
- 보안
- 장애와 재시도
- 확장성과 성능
- 운영과 관측성
- 대안과 결정 근거
- 미확정 사항
- 변경 영향

## 불확실성 처리

기술 구조에 영향을 주는 정책이나 제약이 미확정이면 다음을 제시한다.

- 확인이 필요한 요구사항
- 가능한 구조 선택지
- 비용·성능·복잡도·운영 영향
- ERD·API·배포 영향
- 권장안과 근거

PRD와 충돌하면 Architecture에서 제품 범위를 임의로 변경하지 않는다.

## 출력

- 전체 구조와 인덱스: `docs/Architecture.md`
- 관심사별 상세 설계: `docs/architecture/<concern>.md`
- 새 문서를 만들거나 경로를 변경하면 인덱스를 갱신한다.
- 관련 없는 관심사 문서는 수정하지 않는다.
- 중요한 기술 결정은 `decisions-sync` 대상인지 판단한다.
- ERD, API 또는 Coding Convention 재검토가 필요하면 대상과 이유를 알린다.

## 완료 검증

- PRD 목표와 제약을 만족하는가
- 시스템 경계와 구성 요소 책임이 명확한가
- 주요 처리 흐름이 연결되는가
- 보안·장애·확장·운영 기준이 설명되는가
- 기술 선택의 근거가 있는가
- 설계가 올바른 관심사 문서에 배치되었는가
- 인덱스와 실제 문서 경로가 일치하는가
- 공통 기술 원칙이 중복되지 않는가
- ERD·API 상세를 과도하게 고정하지 않았는가
- 하위 문서의 변경 영향을 식별했는가
