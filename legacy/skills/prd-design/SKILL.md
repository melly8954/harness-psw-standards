# PRD Design

제품 요구사항을 `docs/prd.md`와 `docs/prd/` 하위 문서에 정리한다.

```text
docs/
├─ prd.md
└─ prd/
   └─ <feature>.md
```

- `docs/prd.md`: 제품 목표, 사용자, MVP 범위, 공통 정책과 기능 문서 인덱스
- `docs/prd/<feature>.md`: 기능별 정책, 권한, 흐름, 예외와 완료 기준

## 공통 규칙

작업 전에 `~/.claude/harness/common-execution-rules.md`를 읽고 따른다.

## 입력

필요한 항목만 선택해서 읽는다.

1. 프로젝트 `CLAUDE.md`
2. 사용자 요청
3. 기존 `docs/prd.md`
4. 요청과 관련된 `docs/prd/<feature>.md`
5. 관련된 `docs/decisions.md` 항목
6. 요청에서 직접 참조한 자료
7. 실제 구현이 선행된 경우 관련 코드 또는 운영 자료

`docs/prd/` 전체를 일괄해서 읽지 않는다.

Architecture, ERD, API, App Design은 기존 제품 정책과의 충돌이나 영향 확인이 필요할 때만 읽는다.

## 문서 분류

다음 내용은 `docs/prd.md`에 유지한다.

- 제품 문제와 목표
- 대상 사용자와 핵심 가치
- MVP 범위와 비범위
- 공통 역할과 권한 체계
- 전체 사용자 흐름
- 제품 공통 운영 정책
- 기능 문서 인덱스
- 제품 수준 완료 기준

다음 내용은 `docs/prd/<feature>.md`로 분리할 수 있다.

- 기능 목적과 사용자 가치
- 기능별 사용자 흐름
- 역할별 허용 행위
- 상태와 운영 정책
- 예외와 경계 조건
- 기능 완료 기준

기능 파일명은 소문자 kebab-case를 기본으로 한다.

```text
authentication.md
workspace-management.md
channel-messaging.md
file-sharing.md
```

## 문서 분리 기준

기본적으로 작은 PRD는 `docs/prd.md` 하나로 유지한다.

다음 조건에서는 기능 문서 분리를 검토한다.

- 기능별 정책을 선택해서 읽기 어려울 정도로 문서가 커짐
- 서로 다른 기능의 변경 주기가 명확히 다름
- 권한·상태·운영 정책이 기능별로 독립적임
- 여러 작업이 같은 PRD 구간을 반복해서 수정함

사용자의 요청 없이 기존 PRD 전체를 한 번에 분리하거나 재작성하지 않는다.

## 작업 모드

- 생성: PRD가 없으면 제품 전체 기준과 필요한 기능 문서를 작성한다.
- 수정: 요청과 관련된 제품 정책과 기능 문서만 변경한다.
- 검증: 범위, 권한, 흐름, 정책, 완료 기준과 문서 간 정합성을 점검한다.
- 분리: 문서 규모상 필요하거나 사용자가 요청한 경우 기능별 문서로 분리한다.

## 설계 절차

1. 해결하려는 문제와 대상 사용자를 확인한다.
2. 제품 목표와 성공 기준을 정리한다.
3. MVP 범위와 비범위를 구분한다.
4. 사용자 역할과 핵심 행위를 정의한다.
5. 기능별 정상 흐름과 예외를 정리한다.
6. 권한, 상태, 삭제·보관과 운영 정책을 정리한다.
7. 미확정 사항과 상위 결정이 필요한 내용을 구분한다.
8. 기능별 완료 기준을 정의한다.
9. 하위 설계 문서에 미치는 영향을 확인한다.
10. 루트 인덱스와 기능 문서의 중복을 제거한다.

## PRD 고유 원칙

- 사용자의 문제, 목표와 제품 동작을 정의한다.
- 기술 스택, 테이블·컬럼, 엔드포인트와 코드 구조를 확정하지 않는다.
- 요청되지 않은 기능을 MVP에 추가하지 않는다.
- 기능 설명과 운영 정책을 구분한다.
- 역할, 권한, 상태와 예외를 명확히 한다.
- 비범위를 명시하여 하위 설계의 범위 확장을 막는다.
- 추측이 필요한 정책은 확정 사실로 기록하지 않는다.
- 공통 정책을 기능 문서마다 반복하지 않는다.

## 기능 문서 기준

각 기능 문서에는 필요한 항목만 작성한다.

- 기능 목적
- 대상 사용자
- 선행 조건
- 정상 흐름
- 예외 흐름
- 역할과 권한
- 상태와 정책
- 데이터 보관·삭제 요구
- 알림·외부 연동 요구
- 완료 기준
- 미확정 사항
- 변경 영향

## 불확실성 처리

제품 정책이 미확정이면 다음을 제시한다.

- 확인이 필요한 정책
- 가능한 제품 선택지
- 사용자 경험과 운영 영향
- 하위 Architecture·ERD·API·App Design 영향
- 권장안과 근거

확정 전에는 권장안을 최종 제품 정책으로 기록하지 않는다.

하위 설계에서 현재 정책이 구현 불가능하거나 중대한 위험을 만든다는 근거가 있으면 이를 숨기지 않고 재검토 대상으로 분리한다.

## 기본 문서 구조

### `docs/prd.md`

```text
1. 문서 목적
2. 제품 개요
3. 문제와 목표
4. 대상 사용자
5. 핵심 가치
6. MVP 범위와 비범위
7. 공통 역할과 권한
8. 전체 사용자 흐름
9. 공통 운영 정책
10. 기능 문서 인덱스
11. 제품 완료 기준
12. 미확정 사항
13. 변경 영향
```

### `docs/prd/<feature>.md`

```text
1. 문서 범위
2. 기능 목적
3. 사용자와 권한
4. 정상 흐름
5. 예외 흐름
6. 상태와 운영 정책
7. 완료 기준
8. 미확정 사항
9. 변경 영향
```

필요하지 않은 섹션은 만들지 않는다.

## 출력

- 제품 기준과 인덱스: `docs/prd.md`
- 기능별 정책: `docs/prd/<feature>.md`
- 새 기능 문서를 만들거나 경로를 변경하면 `docs/prd.md`를 갱신한다.
- 관련 없는 기능 문서는 수정하지 않는다.
- 중요한 정책 변경은 `decisions-sync` 대상인지 판단한다.
- Architecture, ERD, API 또는 App Design 재검토가 필요하면 대상과 이유를 알린다.

## 완료 검증

- 제품 문제와 목표가 연결되는가
- MVP 범위와 비범위가 명확한가
- 역할과 권한이 일관적인가
- 정상·예외 흐름이 설명되는가
- 상태와 운영 정책이 충돌하지 않는가
- 기능이 올바른 문서에 배치되었는가
- `docs/prd.md` 인덱스와 실제 문서가 일치하는가
- 공통 정책이 기능 문서에 중복되지 않는가
- 기술·데이터·API 구현을 과도하게 확정하지 않았는가
- 하위 문서의 변경 영향을 식별했는가
