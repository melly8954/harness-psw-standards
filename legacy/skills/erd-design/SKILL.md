# ERD Design

데이터 모델을 `docs/ERD.md`와 `docs/erd/` 하위 문서에 정리한다.

```text
docs/
├─ ERD.md
└─ erd/
   ├─ common.md
   └─ <domain>.md
```

- `docs/ERD.md`: 전체 데이터 모델 지도, 교차 도메인 관계와 문서 인덱스
- `docs/erd/common.md`: 공통 식별자, 시간, 삭제·보관과 네이밍 기준
- `docs/erd/<domain>.md`: 도메인별 엔터티, 관계, 상태, 제약과 인덱스

## 공통 규칙

작업 전에 `~/.claude/harness/common-execution-rules.md`를 읽고 따른다.

## 입력

필요한 항목만 선택해서 읽는다.

1. 프로젝트 `CLAUDE.md`
2. 사용자 요청
3. 관련된 `docs/prd.md` 구간
4. 관련된 `docs/prd/<feature>.md`
5. 관련된 `docs/Architecture.md` 구간
6. 관련된 `docs/architecture/<concern>.md`
7. 기존 `docs/ERD.md`
8. `docs/erd/common.md`
9. 요청과 관련된 `docs/erd/<domain>.md`
10. 관련된 `docs/decisions.md` 항목
11. 요청에서 직접 참조한 자료
12. 실제 스키마가 선행된 경우 관련 마이그레이션

`docs/erd/` 전체를 일괄해서 읽지 않는다.

API와 Coding Convention은 계약 또는 구현 규칙의 정합성을 확인할 때만 읽는다.

## 문서 분류

다음 내용은 `docs/ERD.md`에 유지한다.

- 전체 데이터 모델 개요
- 도메인 경계
- 핵심 엔터티 지도
- 교차 도메인 관계
- 전체 생명주기와 삭제·보관 개요
- 도메인 문서 인덱스

다음 내용은 `docs/erd/common.md`에 유지한다.

- 식별자 정책
- 공통 시간 표현
- 삭제·보관 공통 기준
- 공통 네이밍
- 공통 감사 필드
- 전역 참조 무결성 원칙

다음 내용은 `docs/erd/<domain>.md`에 작성한다.

- 도메인 엔터티와 속성
- 관계와 cardinality
- 상태값과 상태 전이
- unique·check·FK 제약
- 인덱스와 주요 조회 패턴
- 보관·삭제와 이력 구조

## 문서 분리 기준

기본적으로 작은 데이터 모델은 `docs/ERD.md` 하나로 유지할 수 있다.

다음 조건에서는 도메인별 분리를 검토한다.

- 엔터티가 많아 관련 모델만 선택해서 읽기 어려움
- 도메인별 생명주기와 정책이 독립적임
- 교차 도메인 관계보다 내부 관계가 훨씬 많음
- 여러 작업이 같은 ERD 구간을 반복해서 수정함

도메인 간 관계를 각 문서에 중복 정의하지 않는다. 전체 관계는 `docs/ERD.md`에서 요약하고, 관계의 소유 도메인 문서에 상세를 둔다.

## 작업 모드

- 생성: 전체 모델 지도와 필요한 공통·도메인 문서를 작성한다.
- 수정: 요청과 관련된 데이터 모델만 변경한다.
- 검증: 관계, 상태, 제약, 삭제·보관, 조회와 정합성을 점검한다.
- 분리: 문서 규모상 필요하거나 사용자가 요청한 경우 도메인별로 분리한다.

## 설계 절차

1. 관련 제품 정책과 시스템 경계를 확인한다.
2. 핵심 도메인 개념과 생명주기를 식별한다.
3. 엔터티와 식별자를 정의한다.
4. 관계, cardinality와 소유권을 정리한다.
5. 상태값, 상태 전이와 이력 요구를 정의한다.
6. 필수값, unique, check와 참조 무결성을 정리한다.
7. 삭제, 보관, 복원과 개인정보 요구를 검토한다.
8. 주요 조회 패턴과 인덱스 필요성을 검토한다.
9. 교차 도메인 관계와 공통 규칙의 중복을 제거한다.
10. API와 구현 규칙에 미치는 영향을 확인한다.
11. 미확정 사항과 변경 영향을 정리한다.

## ERD 고유 원칙

- 테이블부터 작성하지 않고 도메인 개념과 생명주기를 먼저 분석한다.
- 제품 정책과 Architecture를 데이터 구조로 구체화한다.
- API 경로, 화면 표현과 서비스 계층을 결정하지 않는다.
- 상태값은 의미, 전이와 종료 조건을 함께 정의한다.
- nullable, unique와 FK는 실제 비즈니스 불변식에 근거한다.
- 인덱스는 예상 조회 패턴에 근거하여 정의한다.
- 파생 데이터와 원천 데이터를 구분한다.
- 공통 컬럼을 도메인 문서마다 반복하지 않는다.
- 교차 도메인 관계의 원천을 한 곳으로 유지한다.

## 엔터티 항목 기준

각 엔터티에는 필요한 항목만 작성한다.

- 목적
- 식별자
- 주요 속성
- 상태
- 관계
- 필수·고유·검사 제약
- 생성·변경·종료 조건
- 삭제·보관·복원
- 이력
- 주요 조회
- 인덱스
- 관련 정책

## 불확실성 처리

데이터 모델에 영향을 주는 정책이 미확정이면 다음을 제시한다.

- 확인이 필요한 정책
- 가능한 데이터 모델 선택지
- 정합성·조회·보관·마이그레이션 영향
- API와 운영 영향
- 권장안과 근거

PRD 또는 Architecture와 충돌하면 ERD에서 정책이나 기술 구조를 임의 변경하지 않는다.

## 출력

- 전체 모델과 인덱스: `docs/ERD.md`
- 공통 데이터 규칙: `docs/erd/common.md`
- 도메인별 모델: `docs/erd/<domain>.md`
- 새 문서를 만들거나 경로를 변경하면 `docs/ERD.md`를 갱신한다.
- 관련 없는 도메인 문서는 수정하지 않는다.
- 중요한 데이터 결정은 `decisions-sync` 대상인지 판단한다.
- API 또는 Coding Convention 재검토가 필요하면 대상과 이유를 알린다.

## 완료 검증

- 제품 정책과 데이터 모델이 연결되는가
- 엔터티 책임과 생명주기가 명확한가
- 관계와 cardinality가 일관적인가
- 상태값과 전이가 설명되는가
- 제약이 비즈니스 불변식과 일치하는가
- 삭제·보관·복원 기준이 충돌하지 않는가
- 모델이 올바른 공통 또는 도메인 문서에 배치되었는가
- `docs/ERD.md` 인덱스와 실제 문서가 일치하는가
- 교차 도메인 관계와 공통 규칙이 중복되지 않는가
- API·코드 구조를 과도하게 확정하지 않았는가
- 하위 문서의 변경 영향을 식별했는가
