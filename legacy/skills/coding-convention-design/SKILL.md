# Coding Convention Design

구현 규칙을 `docs/coding-convention.md`와 `docs/conventions/` 하위 문서에 정리한다.

```text
docs/
├─ coding-convention.md
└─ conventions/
   └─ <area>.md
```

- `docs/coding-convention.md`: 공통 구현 원칙과 기술 영역 문서 인덱스
- `docs/conventions/<area>.md`: 백엔드, 프론트엔드, DB, 테스트, Git 등 영역별 규칙

## 공통 규칙

작업 전에 `~/.claude/harness/common-execution-rules.md`를 읽고 따른다.

## 입력

필요한 항목만 선택해서 읽는다.

1. 프로젝트 `CLAUDE.md`
2. 사용자 요청
3. 관련된 `docs/Architecture.md` 구간
4. 관련된 `docs/architecture/<concern>.md`
5. 관련된 `docs/ERD.md` 또는 `docs/erd/<domain>.md`
6. 관련된 `docs/API.md` 또는 `docs/api/<domain>.md`
7. 관련된 `docs/app-design.md` 또는 흐름 문서
8. 기존 `docs/coding-convention.md`
9. 요청과 관련된 `docs/conventions/<area>.md`
10. 관련된 `docs/decisions.md` 항목
11. 요청에서 직접 참조한 자료
12. 실제 코드 스타일 확인이 필요한 경우 관련 코드와 설정

`docs/conventions/` 전체를 일괄해서 읽지 않는다.

## 문서 분류

다음 내용은 `docs/coding-convention.md`에 유지한다.

- 공통 구현 원칙
- 전체 네이밍과 가독성 원칙
- 변경 범위와 최소 수정 원칙
- 공통 품질 기준
- 기술 영역 문서 인덱스

다음 내용은 `docs/conventions/<area>.md`로 분리할 수 있다.

```text
backend.md
frontend.md
database.md
testing.md
git.md
security.md
observability.md
```

코딩 규칙은 비즈니스 도메인이 아니라 기술·구현 영역을 기준으로 분리한다.

## 문서 분리 기준

작은 프로젝트는 `docs/coding-convention.md` 하나로 유지한다.

다음 조건에서는 영역별 분리를 검토한다.

- 백엔드와 프론트엔드 규칙이 함께 있어 선택적 로딩이 어려움
- 테스트·DB·Git 규칙이 독립적으로 커짐
- 기술 영역마다 담당자와 변경 주기가 다름
- 여러 작업이 동일 문서를 반복해서 수정함

세부 주제마다 파일을 만들지 않는다. 관련 규칙을 기술 영역 단위로 묶는다.

## 작업 모드

- 생성: 공통 원칙과 필요한 영역별 규칙을 작성한다.
- 수정: 요청과 관련된 구현 규칙만 변경한다.
- 검증: 기존 코드, 설계 문서와 규칙의 일관성과 적용 가능성을 점검한다.
- 분리: 문서 규모상 필요하거나 사용자가 요청한 경우 기술 영역별로 분리한다.

## 설계 절차

1. 적용할 기술 영역과 코드 범위를 확인한다.
2. 관련 Architecture, ERD, API와 App Design 계약을 확인한다.
3. 기존 코드 스타일과 도구 설정을 확인한다.
4. 네이밍, 패키지·모듈과 계층 규칙을 정리한다.
5. DTO, Entity, 오류, 로깅과 보안 규칙을 정리한다.
6. 테스트, 마이그레이션과 Git 작업 규칙을 정의한다.
7. 자동 검증 가능한 규칙과 사람 판단 규칙을 구분한다.
8. 기존 코드와 충돌하는 경우 적용·전환 범위를 정리한다.
9. 공통 규칙과 영역 문서의 중복을 제거한다.
10. 미확정 사항과 변경 영향을 정리한다.

## Coding Convention 고유 원칙

- 확정된 설계를 일관되게 구현하는 방법을 정의한다.
- 제품 정책, 기술 선택, 데이터 모델과 공개 API를 새로 결정하지 않는다.
- 프로젝트의 실제 언어, 프레임워크와 도구에 맞는 규칙만 작성한다.
- 자동 검증할 수 없는 모호한 표현을 남발하지 않는다.
- 규칙에는 적용 범위, 예외와 예시를 필요한 만큼만 제공한다.
- 기존 코드 전체를 즉시 바꾸도록 강제하지 않고 전환 전략을 고려한다.
- 같은 규칙을 여러 기술 영역 문서에 반복하지 않는다.
- 특정 도메인의 일회성 구현 세부사항을 전역 규칙으로 만들지 않는다.

## 규칙 항목 기준

각 규칙에는 필요한 항목만 작성한다.

- 목적
- 적용 범위
- 필수 규칙
- 허용 예외
- 좋은 예
- 나쁜 예
- 자동 검증 방법
- 기존 코드 전환
- 관련 설계 계약

## 불확실성 처리

구현 규칙에 영향을 주는 기술 결정이 미확정이면 다음을 제시한다.

- 확인이 필요한 기술 또는 도구
- 가능한 규칙 선택지
- 유지보수·검증·전환 영향
- 권장안과 근거

Architecture, ERD 또는 API와 충돌하면 Coding Convention에서 상위 설계를 임의 변경하지 않는다.

## 기본 문서 구조

### `docs/coding-convention.md`

```text
1. 문서 목적
2. 공통 구현 원칙
3. 공통 네이밍
4. 코드 가독성과 변경 범위
5. 공통 품질·보안 기준
6. 기술 영역 문서 인덱스
7. 미확정 사항
8. 변경 영향
```

### `docs/conventions/<area>.md`

```text
1. 문서 범위
2. 구조와 계층
3. 네이밍
4. 데이터·계약 표현
5. 예외·로깅·보안
6. 테스트
7. 자동화와 검증
8. 전환·예외
9. 미확정 사항
10. 변경 영향
```

필요하지 않은 섹션은 만들지 않는다.

## 출력

- 공통 규칙과 인덱스: `docs/coding-convention.md`
- 영역별 구현 규칙: `docs/conventions/<area>.md`
- 새 문서를 만들거나 경로를 변경하면 인덱스를 갱신한다.
- 관련 없는 기술 영역 문서는 수정하지 않는다.
- 중요한 구현 방향 변경은 `decisions-sync` 대상인지 판단한다.
- 실제 코드 또는 설정 변경이 필요하면 대상과 이유만 알리고 요청 없이 수정하지 않는다.

## 완료 검증

- 규칙의 적용 범위가 명확한가
- 실제 기술 스택과 도구에 적용 가능한가
- Architecture, ERD, API와 충돌하지 않는가
- 제품 정책이나 기술 구조를 새로 결정하지 않았는가
- 자동 검증 가능한 규칙이 식별되는가
- 예외와 전환 전략이 필요한 경우 설명되는가
- 규칙이 올바른 공통 또는 기술 영역 문서에 배치되었는가
- 인덱스와 실제 문서가 일치하는가
- 같은 규칙이 여러 문서에 중복되지 않는가
- 구현과 협업에 실제 기준으로 사용할 수 있는가
