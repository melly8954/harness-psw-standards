# App Design

애플리케이션 화면과 상호작용 기준을 `docs/app-design.md`와 `docs/app-design/` 하위 문서에 정리한다.

```text
docs/
├─ app-design.md
└─ app-design/
   ├─ common.md
   └─ <flow>.md
```

- `docs/app-design.md`: 전체 UX 방향, 레이아웃과 화면 문서 인덱스
- `docs/app-design/common.md`: 공통 UI 상태, 접근성, 반응형과 디자인 원칙
- `docs/app-design/<flow>.md`: 기능 또는 사용자 흐름별 화면·상호작용 계약

## 공통 규칙

작업 전에 `~/.claude/harness/common-execution-rules.md`를 읽고 따른다.

## 입력

필요한 항목만 선택해서 읽는다.

1. 프로젝트 `CLAUDE.md`
2. 사용자 요청
3. 관련된 `docs/prd.md` 구간
4. 관련된 `docs/prd/<feature>.md`
5. 관련된 `docs/API.md` 인덱스
6. 관련된 `docs/api/common.md`
7. 요청과 관련된 `docs/api/<domain>.md`
8. 기존 `docs/app-design.md`
9. `docs/app-design/common.md`
10. 요청과 관련된 `docs/app-design/<flow>.md`
11. 관련된 `docs/decisions.md` 항목
12. 요청에서 직접 참조한 자료

`docs/app-design/` 전체를 일괄해서 읽지 않는다.

Architecture와 ERD는 화면 흐름에 직접 영향을 주는 제약을 확인할 때만 읽는다.

## 문서 분리 기준

기본적으로 작은 앱은 `docs/app-design.md` 하나로 유지할 수 있다.

다음 조건에서는 흐름별 분리를 검토한다.

- 특정 기능의 화면과 상태가 독립적으로 큼
- 관련 화면만 선택해서 읽기 어려울 정도로 문서가 커짐
- 기능별 UI 변경 주기가 명확히 다름
- 여러 작업이 같은 문서를 반복해서 수정함

화면 하나마다 파일을 만들지 않는다. 사용자 목표와 흐름이 연결된 화면 묶음을 하나의 문서로 관리한다.

## 작업 모드

- 생성: 전체 UI 방향과 필요한 공통·흐름 문서를 작성한다.
- 수정: 요청과 관련된 화면 흐름과 UI 상태만 변경한다.
- 검증: PRD, API, 접근성, 반응형과 상태 정합성을 점검한다.
- 분리: 문서 규모상 필요하거나 사용자가 요청한 경우 흐름별로 분리한다.

## 설계 절차

1. 관련 사용자 목표와 제품 정책을 확인한다.
2. 진입점과 화면 흐름을 정의한다.
3. 화면별 정보와 행동 우선순위를 정리한다.
4. 권한과 상태에 따른 UI 변화를 정의한다.
5. 입력, 검증, 성공·실패 피드백을 정리한다.
6. 로딩, 빈 상태, 오류와 재시도를 정의한다.
7. 접근성, 키보드와 반응형을 검토한다.
8. API 요청·응답·오류 계약과 정합성을 확인한다.
9. 공통 UI 규칙과 흐름 문서의 중복을 제거한다.
10. 미확정 사항과 변경 영향을 정리한다.

## App Design 고유 원칙

- 제품 정책과 API 계약을 화면 흐름으로 구체화한다.
- PRD에 없는 기능을 UI에서 새로 만들지 않는다.
- API, DB 또는 내부 코드 구조를 임의로 변경하지 않는다.
- 화면의 정상 상태뿐 아니라 로딩·빈 상태·오류 상태를 정의한다.
- 권한 부족과 데이터 없음의 표현을 구분한다.
- 접근성과 키보드 사용을 선택 사항으로 취급하지 않는다.
- 공통 상태와 상호작용을 흐름 문서마다 반복하지 않는다.
- 픽셀 단위 상세보다 구현 가능한 행동·상태 계약을 우선한다.

## 화면 항목 기준

각 화면 또는 흐름에는 필요한 항목만 작성한다.

- 목적
- 진입 조건
- 사용자와 권한
- 레이아웃
- 표시 데이터
- 사용자 행동
- 입력과 검증
- 로딩
- 빈 상태
- 오류와 재시도
- 성공 피드백
- 반응형
- 접근성
- 관련 API
- 미확정 사항

## 불확실성 처리

화면 계약에 영향을 주는 제품 또는 API 정책이 미확정이면 다음을 제시한다.

- 확인이 필요한 정책
- 가능한 UX 선택지
- 사용자·프론트엔드·API 영향
- 접근성과 반응형 영향
- 권장안과 근거

PRD 또는 API와 충돌하면 App Design에서 기능이나 계약을 임의 변경하지 않는다.

## 출력

- 전체 UX와 인덱스: `docs/app-design.md`
- 공통 UI 기준: `docs/app-design/common.md`
- 흐름별 설계: `docs/app-design/<flow>.md`
- 새 문서를 만들거나 경로를 변경하면 인덱스를 갱신한다.
- 관련 없는 흐름 문서는 수정하지 않는다.
- 중요한 UX 정책 변경은 `decisions-sync` 대상인지 판단한다.
- API 또는 Coding Convention 재검토가 필요하면 대상과 이유를 알린다.

## 완료 검증

- 사용자 목표와 화면 흐름이 연결되는가
- PRD의 기능·권한·정책과 일치하는가
- API 요청·응답·오류와 일치하는가
- 로딩·빈 상태·오류·재시도가 정의되는가
- 접근성과 반응형 기준이 설명되는가
- 화면이 올바른 공통 또는 흐름 문서에 배치되었는가
- `docs/app-design.md` 인덱스와 실제 문서가 일치하는가
- 공통 UI 규칙이 흐름 문서에 중복되지 않는가
- API·DB·내부 구현을 임의로 변경하지 않았는가
- 하위 구현 규칙의 변경 영향을 식별했는가
