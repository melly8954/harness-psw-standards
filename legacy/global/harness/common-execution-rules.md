# Common Execution Rules

전역 하네스의 모든 스킬은 이 규칙을 공통으로 따른다.

## 1. 기본 원칙

- 프로젝트 문서는 사실과 결정의 기준이다.
- 스킬은 문서를 읽고 생성·수정·검증하는 절차만 정의한다.
- 요청 범위를 벗어난 기능이나 정책을 임의로 추가하지 않는다.
- 기존 결정을 존중하고 목적 달성에 필요한 최소 범위만 수정한다.
- 작은 기준 문서는 단일 파일로 유지한다.
- 문서가 커져 선택적 로딩이 어려운 경우에만 상세 문서로 분리한다.

## 2. 문서 로딩

작업 시작 시 다음 순서로 필요한 문서만 읽는다.

```text
프로젝트 CLAUDE.md
→ 현재 작업의 루트 기준 문서
→ 요청과 관련된 상세 문서
→ 직접적인 상위 기준 문서 구간
→ 관련 decisions 기록
→ 필요성이 확인된 추가 문서
```

다음 원칙을 따른다.

- `docs/`와 상세 문서 디렉터리 전체를 일괄 로드하지 않는다.
- 루트 문서가 인덱스 역할을 하면 관련 상세 문서만 선택해서 읽는다.
- 문서 전체가 필요하지 않으면 관련 섹션만 읽는다.
- 파일명만으로 책임을 추측하지 않고 루트 문서의 범위 설명을 확인한다.
- 이미 확인한 문서는 최신 상태 확인이 필요한 경우에만 다시 읽는다.

## 3. 기본 문서 의존 순서

```text
prd.md
↓
Architecture.md
↓
ERD.md
↓
API.md
↓
app-design.md
↓
coding-convention.md
```

`decisions.md`는 모든 단계에서 확정된 중요 결정과 변경 사유를 보존한다.

이 순서는 파일 생성 순서가 아니라 결정이 구체화되는 방향이다.

하위 문서는 상위 문서의 결정을 임의로 변경하지 않는다.

## 4. 기준 문서 분리

기준 문서가 커져 관련 내용만 선택해서 읽기 어려운 경우 다음 구조로 분리할 수 있다.

```text
루트 기준 문서
→ 전체 기준, 공통 원칙, 상세 문서 인덱스

상세 문서
→ 기능, 도메인, 기술 관심사, 사용자 흐름 또는 구현 영역의 상세 내용
```

분리 시 다음을 따른다.

- 사용자의 요청 없이 기존 문서 전체를 한 번에 분리하지 않는다.
- 새 상세 문서를 만들거나 이동·삭제하면 루트 인덱스를 함께 갱신한다.
- 공통 정책과 계약을 상세 문서마다 반복하지 않는다.
- 하나의 결정이나 계약을 여러 문서에서 원천처럼 정의하지 않는다.
- 상세 문서의 범위와 로딩 조건은 간결하게 작성한다.
- 관련 없는 상세 문서는 읽거나 수정하지 않는다.
- 구체적인 분리 기준과 출력 경로는 각 설계 스킬을 따른다.

## 5. 불확실한 사항

문서에 결정되지 않은 내용이 작업 결과에 영향을 주면 임의로 확정하지 않는다.

다음을 정리한다.

- 확인이 필요한 내용
- 가능한 선택지
- 각 선택지의 영향
- 권장안과 근거

확정 전에는 권장안을 최종 결정으로 기록하지 않는다.

작업에 영향이 없는 세부 사항은 기존 규칙과 가장 단순한 방식으로 처리할 수 있다.

불가피한 가정은 명시적으로 표시한다.

## 6. 상위 문서 오류

상위 문서의 결정이 기술적으로 불가능하거나 다른 기준과 충돌하면 그대로 구현하지 않는다.

다음을 먼저 정리한다.

- 문제가 되는 기존 결정
- 불가능하거나 충돌하는 근거
- 영향을 받는 하위 문서
- 가능한 수정안
- 권장 수정안

상위 문서를 수정하기 전까지 하위 문서에 다른 결정을 확정하지 않는다.

상위 문서가 수정되면 영향을 받는 하위 문서를 다시 검증한다.

## 7. 문서 수정

- 문서 전체를 다시 작성하기보다 변경이 필요한 부분만 수정한다.
- 기존 용어, 구조, 코드 값과 명명 규칙을 유지한다.
- 요청과 관계없는 문서 분리, 이동과 대량 포맷팅을 하지 않는다.
- 정책 변경 시 직접적인 영향 문서를 함께 확인한다.
- 확정된 중요 변경은 `decisions-sync` 대상인지 판단한다.
- 기존 단일 문서를 분리할 때 원래 의미를 새로 해석하거나 삭제하지 않는다.

## 8. 문서 동기화

문서를 수정한 뒤 다음 불일치를 확인한다.

- 루트 인덱스와 실제 상세 문서 경로
- 용어와 명칭
- 역할과 권한
- 상태와 코드 값
- 데이터 관계
- API 요청·응답
- 화면 동작
- 기술 제약
- 완료 기준
- 결정 기록과 대체 관계

불일치는 하위 문서를 임의로 맞추지 않고 원천 문서부터 수정한다.

## 9. 동시 작업

저장 전에 다음을 확인한다.

- 대상 파일이 처음 읽은 이후 변경되었는가
- 수정 구간이 다른 변경과 겹치는가
- 관련 상위 문서가 변경되었는가
- 현재 작업이 최신 입력을 기준으로 하는가

독립적인 변경은 모두 보존하여 병합한다.

같은 정책이나 구간을 다르게 수정했다면 마지막 저장 우선 방식으로 덮어쓰지 않고 충돌로 보고한다.

관련 상위 문서가 변경되면 하위 작업을 최신 입력으로 다시 검증한다.

## 10. 검증

작업 완료 전 다음을 확인한다.

- 요청 범위를 충족했는가
- 상위 문서와 충돌하지 않는가
- 미확정 내용을 임의로 확정하지 않았는가
- 관련 문서에 누락된 변경이 없는가
- 루트 인덱스와 실제 문서가 일치하는가
- 공통 내용이 상세 문서에 중복되지 않는가
- 구현 가능한 수준으로 구체적인가
- 불필요한 변경이나 과도한 분리가 없는가

검증되지 않은 내용은 완료된 결정처럼 표현하지 않는다.

## 11. 컨텍스트 최적화

- 항상 로드되는 설명은 항목당 200자 이하를 권장한다.
- 스킬 설명과 호출 조건은 짧고 명확하게 작성한다.
- 공통 규칙은 이 문서에만 두고 개별 스킬에서 반복하지 않는다.
- 개별 스킬은 자신의 문서에 필요한 규칙만 가진다.
- 긴 예시와 예외 절차는 실제 조건이 발생했을 때만 읽는다.
- 프로젝트 상세 정보는 프로젝트 `docs/`에만 저장한다.
- 상세 문서를 지나치게 잘게 나누어 탐색 비용을 높이지 않는다.

200자 기준은 프로젝트 설계 문서 전체가 아니라 항상 로드되는 설명과 규칙 항목에 적용한다.

## 12. 책임 분리

```text
전역 CLAUDE.md
= 하네스 진입점과 컨텍스트 라우팅

공통 실행 규칙
= 모든 스킬의 읽기·수정·검증 원칙

harness-structure.md
= 전역 하네스와 프로젝트 문서의 지원 구조

개별 SKILL.md
= 특정 문서를 설계하는 절차와 완료 기준

프로젝트 CLAUDE.md
= 프로젝트 문서 순서와 작업 제한

프로젝트 docs
= 실제 제품과 기술에 대한 결정
```

개별 스킬과 프로젝트 문서는 공통 실행 규칙을 복사하지 않고 참조한다.
